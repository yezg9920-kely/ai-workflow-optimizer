# 修改与回退

对实质修改先写简短目标、范围和可观察的成功条件；检查是否遗漏业务边界、调用方或验证方式。小修改不必建立完整项目体系。

在技能加载目录之外保存待改文件的字节原件。清单记录原路径、备份位置、修改前后 SHA-256、新增文件和改动理由。备份不要被当成第二份技能重新发现。修改前若文件指纹变化，重新阅读，不覆盖并发修改。

优先改明确问题：缩短并限定描述；把分支细节移到有使用条件的参考；将“每次全部读取/全部测试/先更新”改成任务相关条件；写清实际交付与授权内继续的范围。不要用全局禁止或通用口号替换专业知识。

用户提供的事实、领域评分公式、渲染器约束、保存与提交区别、对外授权、已确认母稿和隐私约定不能因精简而丢失。严谨步骤可能正是技能价值，保留具有具体正确性理由的顺序。

保留 frontmatter 的其他支持字段和 UI 调用策略；未要求显式调用模式时，不设置 allow_implicit_invocation: false。第三方方言字段应报告兼容性，不能为通过一个校验器随意删去。

改动后回读文件并比较差异，核对调用方与相对引用。若移动文档，更新相对链接；不要只移动整篇旧流程却仍在入口要求无条件全读。

回退时先比较当前文件与记录的修改后指纹。只恢复属于本轮且没有后续改动的文件；若存在差异，列出冲突并逐项合并。新增文件只有在确认仍属于本轮且无后续引用时才删除。不自动执行批量覆盖或仓库 hard reset。

不得因用户请求优化而自动写入记忆、卸载插件、放宽权限或发布到外部。保留既有授权，缺少的授权只在具体动作前补齐；其余工作继续。
